# [プロジェクト名] Development Tasks

## Status Definitions

- 未着手：対象タスクの作業をまだ開始していない状態。
- 進行中：対象タスクの作業または検証を進めている状態。
- 方針確認待ち：仕様・設計・外部サービスについてユーザーの判断が必要で、その決定を待っている状態。
- ユーザー確認待ち：ユーザーが今すぐ操作・閲覧できる成果物があり、確認手順と期待結果を提示したうえで確認を待っている状態。
- 保留：外部条件や必要な準備が揃わず、対象タスクの実施・検証を一時的に待っている状態。
- 完了：必要な実装・動作確認・テスト・デプロイ確認を終え、完了条件と客観的な証拠が揃った状態。ユーザー確認が受け入れ条件に含まれないタスクはエージェントが完了判定できる。ユーザー確認が必須のタスクは承認まで完了にしない。コードの存在だけでは完了としない。

## Task Definition Rules

各タスクには次を明記する。

- 確認主体：エージェント、ユーザー、または両方
- 確認タイミング：実装直後、画面準備後、マイルストーンなど
- 完了条件：何を満たせば完了か
- 対応テスト：`test-plan.md`のテストID
- 依存完了条件：次のタスクへ進めるための状態
- 証拠：テスト結果、URL、ログ、画面など
- 並列開発をする場合：Wave、担当、主な変更範囲、作業ブランチと統合順序

```text
[ドキュメンテーション：要件定義]
  ↓
[要件分割・依存関係整理・並列化検討]
  ↓
[共通基本設計：DB・API・認証・共通UX等]
  ↓
[必要なPOC・共通設計確定]
  ↓
[独立した個別設計・基盤・主要機能の実装]
  ↓
[ブランチ統合・結合テスト・検証・公開]
```

各段階を一律に直列実行するという意味ではない。依存関係がなく、変更範囲が分離できるPOC・個別設計・実装は途中から並列実行してよい。POCが不要な場合は省略できる。開始時と共通設計・POC完了時に並列化可否を評価する。

## Task Management Rules

- 1つのタスクは、通常1〜2日程度で完了判断できる粒度にする
- 要件定義後に機能・作業単位への分割と依存関係整理を行い、共通設計と個別設計を区別する
- 並列化の開始条件を明確にし、共通設計・POCの完了時にも再評価する。並列化は強制しない
- 技術成立性に不確実性があり、失敗時に大きな手戻りが発生する要素は、本実装より先にPOCタスクを作成する
- POCタスクには目的、成功条件、対応テストID、証拠を明記する
- POCの技術的な成功・失敗は、エージェントが事前に定めた成功条件と証拠に基づいて判定できる。ただし、POC結果に基づく重要なアーキテクチャの採用・変更は、別途ユーザー承認を得る
- POCが必要な本実装タスクは、対応POCタスクの`完了`を依存条件とする
- 依存タスクが`完了`でない限り、依存先のタスクを開始しない
- 確認待ち・保留の理由と再開条件を記録し、依存しない作業は継続する
- 合意済み範囲内のタスク分割・順序調整はエージェントが自律的に行い、このファイルを更新する。MVP、受け入れ条件、重要な依存関係を変更する場合は事前にユーザー承認を得る
- 完了時には必ず証拠を記録する
